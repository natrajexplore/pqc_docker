# Security model of the lab itself

WireScope demonstrates security protocols, so it should not be the weakest
thing on your laptop. This page says what it protects, what it doesn't, and why
each privilege exists. Keep it current when you change a privilege.

## Scope

A single-user lab on a workstation. It is **not** a production template and
**not** a multi-user service. Every key, certificate, PSK and PPK is lab-only.

## Threats considered and mitigations

| Threat | Mitigation |
|---|---|
| Anyone on your LAN reaches the UI and drives containers | UI published on `127.0.0.1` only; backend and agents are not published at all |
| A website you visit drives the API through your browser (CSRF, cross-site WebSocket, DNS rebinding) | backend rejects any request whose `Host` is not in `PQCW_ALLOWED_HOSTS` and any request whose `Origin` differs from `Host` (`backend/app/middleware.py`); nginx forwards the real `Host:port` |
| Backend compromise = root on the host via docker.sock | backend never mounts the socket; `socket-proxy` blocks images, volumes, networks, build, swarm, secrets; socket mounted read-only into the proxy. **Gap:** tecnativa's `CONTAINERS=1` + `POST=1` also permits `POST /containers/create`, so a compromised backend could still start a privileged container. Closing this needs a proxy with per-method path allowlists (e.g. allow only `POST /containers/{id}/exec` and `POST /exec/{id}/start`) |
| A lab container calls the Docker API | `socket-proxy` sits alone with the backend on `pqcw_dockerapi` (`internal: true`); lab nodes are only on `pqcw_mgmt` and cannot reach it |
| A lab container calls the capture agent API | agents bind to their mgmt address only, require `X-PQCW-Token` (random per checkout, from `.env`, compared in constant time) and refuse to start without one; rejected calls are logged |
| Secrets leak through git | PSK/PPK/token generated by `make secrets` into `.env` (gitignored, mode 600); IPsec secrets rendered at start-up into `/run/pqcw` inside the container; PKI minted into named volumes, not bind mounts |
| Command injection through scenario or API input | all exec calls use argv lists; tshark/dumpcap never run through a shell; `run_id` and BPF filter validated by regex; scenario files are trusted repo content, not user input |
| Path traversal on pcap download | downloads resolved and checked to be under the captures directory |
| Oversized uploads | imports capped at 50 MB (nginx and backend) |
| Long-running or hung steps | every non-detached exec wrapped in `timeout`; whole run bounded by `PQCW_RUN_TIMEOUT_S`; one run per stack |
| Container escape surface | no `privileged`; `cap_drop: [ALL]` on agents/backend/frontend with only NET_RAW/NET_ADMIN where capture or XFRM needs it; `no-new-privileges` everywhere; read-only root filesystems for backend and frontend |
| Browser-side attacks on the UI | CSP, `X-Frame-Options: DENY`, `nosniff`, no third-party scripts (fonts only) |

## Deliberate lab-only weaknesses

- **TLS key logs.** Scenarios with `keylog:` write the session secrets so the
  analyzer can decrypt TLS 1.3 Certificate messages. This is what makes ML-DSA
  authentication *wire* evidence instead of a claim. Disable with
  `PQCW_ALLOW_TLS_KEYLOG=false`. Never copy this pattern anywhere real.
- **Unencrypted private keys** in the PKI volumes, and a shared CA key reachable by
  both peers. `make nuke` deletes them.
- **`StrictModes no`** in sshd because keys live in a volume with host ownership.
- **Capture volume is world-writable (1777)** so the unprivileged backend can write
  next to root-owned agent output.
- **Upstream images run as root** inside their containers (strongSwan, hostapd,
  sshd need it); they are confined by capabilities, not by user.
- **The backend API has no authentication of its own.** Lab nodes share
  `pqcw_mgmt` with it and can call `backend:8000` directly (the Host check only
  stops browsers). Acceptable because lab nodes run only trusted repo content.
- **Imported pcaps are parsed by tshark**, a large attack surface. It runs as an
  unprivileged user with no capabilities on a read-only root filesystem.

## Observability

- Every backend log line carries a request id. nginx generates it, logs it as
  `rid=` and forwards it as `X-Request-ID`; the backend echoes it in the response
  and stamps it on every line, including lines from the run that request started.
- `PQCW_LOG_FORMAT=json` switches the backend to one JSON object per line.
- Logged security events: rejected Host/Origin (backend), bad agent token (agents).
- Run lifecycle (start, step failure, finish with status/packets/duration) and
  imports are logged at INFO.
- backend, frontend and capture agents have Docker healthchecks (`make ps`).

## Privileges by container

| Container | Capabilities | Why |
|---|---|---|
| ipsec-*, ipsec-auth-* | NET_ADMIN, NET_RAW | install XFRM SAs/policies; ping/tcpdump |
| macsec-* | NET_ADMIN, NET_RAW | create the veth pair; raw EAPOL sockets |
| tls-*, ssh-* | NET_RAW | tcpdump inside the container (upstream habit) |
| cap-* | NET_RAW, NET_ADMIN (all others dropped) | live capture with dumpcap/tshark |
| backend, frontend | none | |
| socket-proxy | default | it is the boundary; keep its env allowlist minimal; reachable only from the backend |

## Reporting

This is a personal lab project. If you find something, open an issue on the
GitHub repository rather than a public exploit write-up.
